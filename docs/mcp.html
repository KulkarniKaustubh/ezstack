MCP Server
for Claude Code

ezstack ships a standalone Model Context Protocol server, ezs-mcp, that exposes the core stack operations as MCP tools. Point Claude Code (or any MCP-compatible agent) at it and it can drive ezs directly — status, list, sync, push, PR create/merge, goto, new, delete, reparent.

$ claude mcp add ezstack -- ezs-mcp --repo "$(pwd)"
About the Model Context Protocol
How It Works

One binary. Eleven tools. Real ezs under the hood.

ezs-mcp is a separate binary that speaks JSON-RPC over stdio. Under the hood it invokes the same ezs command functions your shell uses — there is no second copy of the logic to drift. Your agent gets the identical behavior you'd get from the terminal, captured and handed back as structured tool results.

1

Stack-aware from the first call

Read-only tools return JSON by default so the agent can reason about the stack shape, or pass decorated=true to get the terminal-styled output you'd see from ezs status. Pin the server to a specific repo with --repo so it behaves predictably when Claude launches it from a parent workspace directory.

# Agent asks: "what does the stack look like?"
→ ezstack_list { "all": true }
  returns JSON: every stack, branch, parent, PR state, CI status

# Or request the pretty version:
→ ezstack_status { "decorated": true }
  returns the same colored tree you see in a terminal
2

Destructive tools are tagged

Tools that rewrite history or mutate remote state (ezstack_sync, ezstack_push, ezstack_delete, ezstack_pr_merge) carry the MCP destructive annotation, so clients like Claude Code can prompt the user before executing them. Read-only tools carry the read-only annotation and run without interruption.

# Claude Code sees the annotation and asks:
⚠  Tool ezstack_sync is marked destructive.
   Run with { "all": true } ?
   [Y]es / [N]o / [A]lways allow this tool
3

No hidden interactive prompts

Branch-management tools like ezstack_goto, ezstack_new, ezstack_delete, and ezstack_reparent mark their positional arguments as Required in the tool schema, so the agent cannot call them with missing args — preventing fallthrough to fzf-backed interactive selection that would hang in a no-terminal context. Internal yes/no prompts are auto-accepted for destructive tools (the client already confirmed via the annotation).

# Schema rejects the call before it runs:
→ ezstack_delete {}
✗ error: missing required argument "branch"

# Properly formed call runs without waiting on a prompt:
→ ezstack_delete { "branch": "feature-part2" }
✓ deleted feature-part2 and its worktree
Tool Catalog

Eleven tools, full stack coverage

Every core ezstack operation an agent needs — inspect, mutate, push, PR — exposed with strict input schemas. Read-only tools default to JSON; destructive tools carry the MCP destructive annotation.

Tool Annotation Description
ezstack_status read-only Current stack with PR and CI status. all, decorated.
ezstack_list read-only List all stacks and branches. all, decorated.
ezstack_sync destructive Rebase (or merge) stack branches with their base. stack, all, current, parent, children, merge, dry_run.
ezstack_push destructive Push current branch or entire stack. stack, force.
ezstack_pr_create — Create a pull request for the current branch. title, draft.
ezstack_pr_stack — Update every PR description in the stack with navigation links.
ezstack_pr_merge destructive Merge the pull request for the current branch.
ezstack_goto — Switch to a branch in the stack. branch (required).
ezstack_new — Create a new branch in the stack. name (required), parent.
ezstack_delete destructive Delete a branch and its worktree. branch (required).
ezstack_reparent — Move a branch to a new parent. branch and new_parent (both required).

Installation

Install the ezs-mcp binary, then register it once with your MCP client. The server is pinned to a repository via --repo, so it keeps working even when the client launches it from a parent workspace directory.

Homebrew (macOS / Linux)

The ezstack formula installs both ezs and ezs-mcp side by side.

$ brew tap KulkarniKaustubh/ezstack
$ brew install ezstack
  → installs both ezs and ezs-mcp

Go install

Fetch the MCP server directly from the module proxy. Same command works for a specific tag or @latest.

$ go install \
    github.com/KulkarniKaustubh/ezstack/v4/cmd/ezs-mcp@latest

From source

Clone the repo and build both binaries with a single make target.

$ git clone https://github.com/KulkarniKaustubh/ezstack.git
$ cd ezstack
$ make install-all
  → installs ezs and ezs-mcp to ~/.local/bin

Register with Claude Code

Run this once inside any ezstack-configured repo. Claude Code will launch ezs-mcp on demand and route tool calls to it.

$ claude mcp add ezstack \
    -- ezs-mcp --repo "$(pwd)"
✓ added MCP server "ezstack"

Flags & environment

ezs-mcp is minimal on purpose — one flag and one optional environment variable.

Name Type Description
--repo <path> flag Absolute path to the git repository root. The server cds here at startup so every tool call operates against the same repo regardless of where the client launched the process from.
EZSTACK_HOME env var Override the ezstack config directory (defaults to ~/.ezstack). Useful for isolated test environments.
Safety

Built for agents that share a process

MCP servers receive concurrent tool calls, and ezs operates on global process state (stdout/stderr, the ezstack ui.Backend, working directory). ezs-mcp is explicitly engineered to keep those invariants intact.

1

Serialized tool execution

Every tool handler acquires a process-wide mutex before running, so two concurrent calls from the agent are serialized rather than racing on shared globals (stdout/stderr swaps, ui.Backend replacement, ui.YesMode). The race detector is clean under go test -race.

2

Deadlock-safe output capture

Stdout and stderr from each ezs invocation are captured via concurrent pipe drainers started before the command runs — so large outputs (ezs list --all against a huge repo, verbose ezs sync traces) can't block on the ~64 KB OS pipe buffer.

3

CI-backed install contract

The release pipeline verifies go install github.com/.../ezs-mcp@<tag> resolves and the resulting binary is executable on every tagged release, and a stdio integration test boots the real binary, lists tools, and round-trips calls against a temp repo on every PR. If the install contract ever drifts, CI fails before users see it.
